# Проектная работа «WebLarek. Плохой сервер», спринт 17

Аудит безопасности интернет-магазина «Web-ларёк»: найдены и устранены уязвимости
в бэкенде и клиенте, обновлены зависимости, приведён в порядок линтинг.

- Репозиторий: https://github.com/kartruex/bad-server
- Автор: Андрей Дьяченко, 46 когорта, курс «Fullstack базовый»
- Опубликованная версия: проект на сервере не публиковался, запускается локально

## Запуск

1. Создать файлы окружения из примеров и заменить секреты:

```bash
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

Для запуска в Docker в `backend/.env` нужен адрес базы
`mongodb://root:example@mongo:27017/weblarek?authSource=admin`,
а в `frontend/.env` — `VITE_API_ORIGIN=http://localhost/api`.

2. Запустить контейнеры:

```bash
docker compose up -d
```

3. Наполнить базу данными из [.dump/README.md](.dump/README.md).
4. Магазин доступен на http://localhost/, вход — http://localhost/login/,
   админка — http://localhost/admin/.

## Что исправлено

### XSS

Комментарии к заказам, адреса, названия и описания товаров очищаются от разметки
(`sanitize-html`) на этапе валидации, до записи в базу. В админке и личном кабинете
комментарий выводится средствами React, вызовы `dangerouslySetInnerHTML` удалены,
поэтому пользовательские данные не попадают в DOM как разметка.

### CSRF

Добавлен эндпоинт `GET /auth/csrf-token`, который выдаёт токен и ставит httpOnly-куку
`_csrf`. Все небезопасные методы (POST, PATCH, DELETE) проходят через `csrf-csrf`:
сервер сверяет заголовок `X-CSRF-Token` с подписанным значением куки. Клиент получает
токен автоматически и повторяет запрос при его устаревании.

### NoSQL-инъекции

- Параметры запроса валидируются схемами Joi (`celebrate`): `status`, `sortField`
  и `sortOrder` принимают только значения из белого списка, поэтому объект вида
  `status[$expr][$function]` больше не попадает в `$match`.
- `email` при входе и идентификаторы из токенов приводятся к строке и `ObjectId`.
- Обновление профиля и клиента принимает только поля `name`, `email`, `phone`:
  раньше тело запроса уходило в апдейт целиком и позволяло выдать себе роль администратора.

### Переполнение буфера

Ограничены размер тела запроса (`BODY_LIMIT`, по умолчанию 100kb), длины всех
пользовательских строк, количество товаров в заказе, а также размер (от 2 КБ до 10 МБ),
количество и тип загружаемых файлов. Параметры `page` и `limit` нормализуются: `limit`
обрезается до 10, поэтому одним запросом нельзя выгрузить всю коллекцию.

### ReDoS

Регулярное выражение для телефона заменено на линейное с жёстким ограничением длины —
прежнее `/^(\+\d+)?(?:\s|-?|\(?\d+\)?)+$/` содержало вложенные квантификаторы и давало
экспоненциальный откат. Строки поиска экранируются перед созданием `RegExp`
и ограничены по длине.

### DDoS

Подключён `express-rate-limit`, настраиваемый переменными `RATE_LIMITED`,
`RATE_LIMIT_POINTS` и `RATE_LIMIT_DURATION`. Добавлен `helmet`, отключён заголовок
`x-powered-by`, обработчик ошибок больше не пишет в лог каждый ответ 4xx и не раскрывает
стектрейсы. Статика и каталог товаров отдаются с заголовками кеширования, nginx кеширует
ассеты и скрывает свою версию.

### Path Traversal

Middleware статики приводит путь к абсолютному и проверяет, что результат остался внутри
разрешённой директории; обрабатываются URL-кодирование и нулевой байт. Имя загруженного
файла генерируется сервером (UUID и расширение по MIME-типу), а не берётся из
`originalname`, а перенос файла из временной папки идёт только по `basename`.

### Аутентификация и права доступа

Пароли хранятся в виде bcrypt-хеша вместо md5. Списки заказов и клиентов, а также
загрузка файлов доступны только администратору. Время жизни access-токена сокращено
с 10 лет до 10 минут.

### Зависимости и линтинг

`npm audit` в `backend` и `frontend` возвращает 0 уязвимостей. Удалены неиспользуемые
пакеты. `npm run lint` и сборка проходят без ошибок и предупреждений в обоих пакетах.

## Проверка

```bash
cd backend && npm audit && npm run lint && npm run build
cd ../frontend && npm audit && npm run lint && npm run build
```

Нагрузочную проверку можно выполнить Apache Benchmark, лимит запросов при этом
поднимается через `RATE_LIMIT_POINTS` и `RATE_LIMIT_DURATION`:

```bash
ab -k -c 200 -n 5000 http://localhost/
```
